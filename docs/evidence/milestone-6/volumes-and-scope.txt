Architectural note: why 2 volumes is the correct, complete count
----------------------------------------------------------------------
CivicPulse's triage/LLM feature is served by an EXTERNAL, cloud-hosted LLM
API (Groq/Grok-compatible API key, configured via LLM_API_KEY / LLM_MODEL
in .env; see compose.yaml's `backend` service environment block and
backend/app/core/config.py). There is no self-hosted Ollama container in
this stack (confirmed: no `ollama` service definition in compose.yaml or
compose.prod.yaml, and TRIAGE_PROVIDER supports `llm | rules | simulated`
where `llm` calls the external hosted API rather than a local model
runtime).

Consequently, an `ollama_models` volume — which would only exist to cache
locally-pulled model weights for a self-hosted Ollama container — is
architecturally N/A, not missing. The system has exactly two stateful
services that require durable storage across container recreation:

  1. pgdata     — PostgreSQL data directory (/var/lib/postgresql/data).
                  Required: complaint records must survive redeploys.
  2. redisdata  — Redis AOF persistence (/data, `--appendonly yes`).
                  Required: cache/rate-limit state survives restarts
                  (though Redis here is a cache, not a system of record).

Under this cloud-LLM architecture, 2 named volumes represents 100%
compliance — there is no third volume to be "missing." Verified in this
session via `docker compose up -d` / `down` / `up -d` (see
postgres-persistence.txt): pgdata correctly persisted a real inserted row
across a full container lifecycle.

Result: PASS — 2/2 required volumes present; ollama_models correctly
absent per the documented cloud-LLM architectural choice.
